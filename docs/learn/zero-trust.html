Zero Trust

Zero Trust is a rule more than a product: never let a request in because of where it comes from; check who it is, every time. Cloudflare's version of it is what puts a login page in front of your hosted copy.

The old way: castle and moat

Companies used to put a wall (firewall, VPN) around the office network and trust everything inside. Once you were "in", by sitting at an office desk or turning on the VPN, every internal app opened for you. The weakness: one stolen laptop or VPN password, and the attacker is inside the castle with everyone's trust.

Zero Trust drops the idea of an inside. Every app has its own guard, and every request must show proof of identity, no matter which network it came from. Being on your home Wi-Fi earns nothing.

Cloudflare One, Zero Trust and Access: which is which

The dashboard you just closed mixes these names, so here's the map:

  • Cloudflare One is the brand for the whole security suite.
  • Zero Trust is the dashboard section and plan name. You're on Zero Trust Free, team your-team. The card you entered when activating it is for upgrades; the free plan doesn't charge it.
  • Access is the one feature we use: the guard at the door of an app. It's the item "Protect an application with Access" that shows as done on that page.

The unticked items on that page (enroll a device, add a DNS location, add a SaaS integration) belong to the other features: replacing a company VPN, filtering a company's DNS, watching Google Workspace. A one-person focus app needs none of them, which is why nothing there is left to do.

What happens when you open the hosted copy

  1. Your browser asks for kitestring.custom-pomodoro.workers.dev. Access sees no login cookie and redirects you to your-team.cloudflareaccess.com.
  2. You type your email. Access can email you a one-time PIN. A comment in deploy/wrangler.jsonc says the Access app is email-only. The allow-list itself is not in git, so this lesson does not name who is on it.
  3. You enter the PIN. Access sets a cookie and, on every later request, attaches a signed token in a header called Cf-Access-Jwt-Assertion.
  4. The request reaches our Worker with that token.

The token, and why the Worker checks it again

The token is a JWT (JSON Web Token): three base64url chunks joined by dots. Base64url uses - and _, and it leaves the padding off. b64url in the Worker puts the padding back before atob. A header says which key signed it. A payload carries your email, which app, and when it expires. A signature closes the token.

eyJhbGciOiJSUzI1NiIsImtpZCI6…   ← header   { alg: "RS256", kid: "…" }
.eyJlbWFpbCI6InByYXguc3Iu…     ← payload  { email, aud, iss, exp }
.Q2xvdWRmbGFyZSBzaWduZWQ…      ← signature, made with Cloudflare's private key

Cloudflare signs with a private key only it holds and publishes the matching public keys at https://<team>/cdn-cgi/access/certs. The Worker caches those keys for 10 minutes. Anyone can check a signature with the public key. Nobody can make one without the private key. verifiedEmail() in worker/index.ts returns null if the token is missing or does not split into three parts. It then checks:

  1. The algorithm is RS256 (so nobody can sneak in "alg: none").
  2. The kid is one of the team's current public keys, and the signature matches that key.
  3. aud (audience) is this app's ID, so a valid token for some other Access app can't be reused here.
  4. iss (issuer) is https:// plus the team domain (https://your-team.cloudflareaccess.com). The bare domain is not enough.
  5. exp hasn't passed. nbf more than 60 seconds in the future is rejected too.

email has to be a string. The Worker lowercases it, and that string is the row owner in D1. That's defence in depth: if Access were ever misconfigured, or someone reached the Worker another way, a forged or missing token still gets nothing. The Worker does not redirect. It answers HTTP 401 and { ok: false, error: "not signed in" }. Access itself can still send a browser with no cookie to the login page, before the Worker runs.

Where the analogy stops

"A guard at every door" makes it sound like many guards. For us it's one Access policy covering one hostname, plus the Worker's own token check. Zero Trust is a rule you can follow at any size.

Check yourself

An attacker copies a real, unexpired Access token from a different Cloudflare Access app on the same team and sends it to /api/sync. The signature is genuine. Which of the five checks stops them?

Show the answer

The audience check (aud). The token is properly signed by your team and not expired, but its aud is the other app's ID, not Kitestring's POLICY_AUD. Without that check, any app on the team could unlock every other app's data.
