Lesson 3 of 6

Where your data lives

Your tasks and stats have a home on your machine first. On the hosted copy they also get a second home in the cloud, so another device can pick them up.

Home one: IndexedDB, inside the browser

Every browser ships a small database called IndexedDB. Each website gets its own private one, keyed by its address. Kitestring saves seven sync records in it, each a whole JSON value under one name:

settings   → { timer: { lengths: { pomodoro: 25, short: 5 … } … } }
tasks      → [ { id, title, done, etaMin, … }, … ]
focusPick  → a task id, or null
stats      → { chunks, tasksDone }
notes      → your notepad text
mixer      → saved sound mixes
radio      → favourite stations

Those seven names are SYNC_KEYS. IndexedDB also holds timer, customBgs, image blobs named custom-bg:<id>, and sync-meta. A stats chunk has id, kind (focus or break), segment (focus, short or long), start, ms, completed, and sometimes segId and taskId. day is not stored. dayKey works it out later. focusPick is an id, not the task.

This is a key-value layout: one name, one blob. No tables, no SQL. It fits because the app always reads a whole list at once (all tasks, all stats) and nothing ever needs "find tasks where…" across millions of rows.

The "address" detail that surprises people

IndexedDB is keyed by origin, meaning scheme + host + port. So these are four different databases that never see each other:

CopyOriginIts own IndexedDB
MAC Chrome via companionhttp://localhost:4747in Chrome's profile
MAC Same companion, other hosthttp://127.0.0.1:4747a separate Chrome database
CLOUDFLARE Hosted copyhttps://kitestring.custom-pomodoro.workers.devin whichever browser opened it
MAC Mac appapp://custom-pomodoroin the app's own Electron profile

The companion binds 127.0.0.1 and also allows localhost. Those two strings are different origins.

That's why the Mac app started empty, and why Settings → Your Data has Export and Import. A backup carries settings, the timer, tasks, focusPick, stats, notes and mixes. Radio favourites stay behind. Custom background images stay behind. The export message says those images stay in this browser. The timer is in the file, and the timer is not a sync key, so a later sync does not carry it.

Home two: D1, at Cloudflare

D1 is Cloudflare's hosted database. Under the hood it's SQLite, the same small SQL engine inside every iPhone, run on Cloudflare's machines. The app uses exactly one table:

CREATE TABLE kv (
  email      TEXT,     -- who (from the verified login, lesson 5)
  key        TEXT,     -- "tasks", "stats", …
  value      TEXT,     -- the same JSON as in IndexedDB
  updated_at INTEGER,  -- when this copy was last changed (ms)
  PRIMARY KEY (email, key)
);

It's the same key-value shape as IndexedDB, plus an email column so two people could never see each other's rows. The database is named custom-pomodoro-sync and lives in your Cloudflare account. Nobody else hosts it.

How the two homes agree

The rule lives in one small function, decide() in src/lib/sync.ts: if the cloud's timestamp is newer, pull; if mine is newer, push; if equal, do nothing. The rule is called last writer wins. A pull also runs when a hidden tab becomes visible again (visibilitychange). Focusing a window that was already on screen does not pull.

Where last-writer-wins falls short

It works per key, not per task. If the laptop adds task A and the phone adds task B while both are offline, whichever saves last replaces the whole tasks list, and the other new task is lost. For one person who mostly uses one device at a time that's an acceptable trade. Merging properly needs per-item timestamps or a CRDT (a data type built to merge edits made in two places), which is a lot more code.

Why not just put everything in the cloud?

  • Speed: reading from disk on your machine is roughly instant. A round trip to a server is much slower, and it can fail.
  • Offline: the timer never waits for Wi-Fi.
  • Privacy: the localhost and Mac copies send your data nowhere at all. Sync is switched off there on purpose. syncAllowedAt() in src/lib/sync.ts allows it only on the hosted https copy. app:// is off too.

Check yourself

You add three tasks in the Mac app. Then you open the hosted copy on your phone. Do the three tasks show up? Explain using origins.

Show the answer

No. The Mac app's data lives in the IndexedDB for app://custom-pomodoro. syncAllowedAt() keeps that origin from syncing, so D1 never sees those three tasks. The phone reads the workers.dev origin. To move them: Export in the Mac app, Import on the hosted copy, then let that copy sync. Import writes the file into this browser and stamps the imported sync keys in sync-meta through metaAfterImport, so the hosted copy uploads those keys. The phone pulls that upload.
