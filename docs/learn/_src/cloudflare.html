Cloudflare, not Vercel

Both companies put your site on computers all over the world. For this app Cloudflare won on three things: a free login wall, a free database next to the code, and no surprise public deploys.

What these companies actually are

When someone types a web address, a computer somewhere has to answer with your files. Running that computer yourself means keeping it patched, online and fast for people far away. Hosting platforms rent you a share of thousands of machines instead.

  • Cloudflare started as a network in front of other people's websites: it speeds them up and blocks attacks. It runs data centres in many cities. Later it let you run your own code on those same machines.
  • Vercel started as the home for Next.js apps. It's built around git: push a branch, get a preview URL, merge, get production. It's very good for teams shipping React sites.

The three Cloudflare pieces we use

Workers

A Worker is a small function Cloudflare runs for a request, in whichever city is closest to the visitor. It isn't a server you keep switched on. A cold start is fast, on the order of milliseconds. After that, one instance can handle more than one request, including several at once, on one event loop. Ours is worker/index.ts, about 130 lines. run_worker_first in deploy/wrangler.jsonc is ["/api/*"], so every /api path runs the script. /api/me is GET. /api/sync is GET and PUT. Any other /api/ path returns 404 JSON. Paths outside /api/ do not run the script. The assets layer serves those files. env.ASSETS.fetch at the bottom of the Worker is only a fallback if the script is invoked anyway.

Static assets

The same Worker project carries the dist/ folder. Requests for /, the JS or the sounds are answered straight from Cloudflare's file store without running any of our code. That's both fast and free.

D1

The database from lesson 3. The Worker reaches it through a binding named DB: a direct handle Cloudflare wires in, so there's no database password in the code at all.

Deploying is the build, then one pinned command: npm run build && npx wrangler@4.152.0 deploy -c deploy/wrangler.jsonc. Wrangler is Cloudflare's command-line tool. It uploads the Worker code and the dist/ files and connects the D1 binding. It does not build dist/. The pin is Wrangler 4.152.0.

Why not Vercel

NeedCloudflare (free)Vercel Hobby (free)
Keep the site private behind your own loginAccess is free for up to 50 users and covers productionPreview links are covered on Hobby. Password Protection for production is not on Hobby. On Pro it is 20 dollars per protected project. Hobby can still require a Vercel account login on production. That login is a team account. Access is an email allow-list.
A database for syncD1 sits in the same account, reached by bindingVercel no longer runs its own Postgres or KV; you'd add a third-party database from the Marketplace
What happened in practiceFrom memory, deploys were checked with an anonymous request, and that request landed on the login page.From memory, the first deploy of a new project went straight to public production, twice, even when a preview was asked for. Both had to be deleted.
Commercial useThis app uses the free Workers plan. Check Cloudflare's current terms before treating commercial use as allowed.Hobby is for personal, non-commercial use

None of this makes Vercel bad. For a team shipping a public Next.js site with preview links per pull request, it's often the nicer tool. This app needed private-by-default and a free database, and Cloudflare had both in one place.

What we gave up

Vercel's git integration (automatic preview per branch) is smoother. On Cloudflare the deploy is by hand. Build with npm run build, then run npx wrangler@4.152.0 deploy -c deploy/wrangler.jsonc. Wrangler uploads dist/ and does not build it. For a one-person app that's fine. With a team you'd wire it into GitHub Actions.

Show the answer

Access runs first and bounces them to the login page if they aren't signed in. Access sits in front of everything on that hostname. If they are signed in, our Worker code does not run: the path doesn't start with /api/, so Cloudflare answers straight from static assets.
